ihris-dak-data-dictionary/v1One sheet of a WHO SMART Guidelines DAK (L2) data dictionary, derived from one iHRIS record form class. Each element row carries the columns of the WHO 'Form data mapping guide' (Digital transformation handbook for primary health care, 9789240093362, pp. 86-90), plus the provenance of the iHRIS field it was derived from. Columns the source cannot answer (description, activity, conditionality, indicator and decision-support linkages) are null until authored: they are never inferred.by $schema tag

ihris-dak-proposal/v1An AUTHORED overlay on the derived DAK: a proposal a person makes, with its rationale and evidence, about something the source does not state (a binding, a definition, a mapping). Lives in src/ihris-data-dictionary/authored/, which no build writes. `status` moves proposed -> accepted/rejected only by the owner's decision.by $schema tag
ihris-dak-value-sets/v1Which iHRIS list backs each value set, which data elements use it, and how many default and sample codes ship (src/ihris-data-dictionary/value-sets.json).src/ihris-data-dictionary/value-sets.json
ihris-data-list/v1The records one iHRIS package ships for one list form (//I2CE/formsData/forms/<form>/<id>) in a release, each attributed to the module that ships it. `provenance` separates a module's DEFAULT data, installed with the module (e.g. ISO countries, gender), from SAMPLE data (SampleData-* modules and sites), which illustrates one country's lists and must never be read as a standard code set.by $schema tag
ihris-form-class/v1One I2CE form class (e.g. iHRIS_Person) in a release, with the fields EVERY module contributes to it merged in, and each field attributed to the module that declared it. This is the iHRIS data model: the analogue of a DAK core data element set, read from the source rather than from documentation.by $schema tag
ihris-github-inventory/v1A path inventory of a GitHub repository pinned at one commit (src/ihris5/inventory/*.json). Paths and FSH definition headers only: nothing is copied.src/ihris5/inventory/*.json
ihris-i2ce-module/v1One I2CE module as declared by its <I2CEConfiguration> <metadata> in a specific release. Modules are the unit of iHRIS functionality: each declares what it needs (requirement), turns on (enable), refuses (conflict), and which forms and pages it contributes. Transcribed from the module's XML file inside a checksum-verified release tarball. The XML itself is not copied; `source` pins it by path and sha256.by $schema tag
ihris-ig-build-patches/v1Fixes applied to a WORKSPACE copy of a sub-instance's declared IG source before fhir-harness builds it (src/tools/apply_ig_patches.py). Each entry is an upstream defect to report, removed when the pinned source fixes it.src/*/ig-build-patches.json
ihris-instance-extension/v1The ihris-specific keys of an instance declaration (ihris.json and each <name>.json). folio-assistant's CatHarnessDeclarationSchema validates the rest (src/tools/validate-folio.ts), and zod drops keys it does not declare, so these are checked here. Only the keys below are constrained; the platform's keys pass through. A `stated` licence may carry an `images` permission for parts its licence does not cover.by $schema tag

ihris-source-record/v1What a version-control host says about one node of a source catalogue: a project, a release series (and its branch), a release (and its files, with checksums), or a git repository pinned at a commit. Nothing here is the source itself. Everything is a statement about a source that stays upstream.by $schema tag
ihris-toolkit-stage/v1One stage of the iHRIS Implementation Toolkit (toolkit.ihris.org) as the site structures it: an ordinal stage with an introduction, objectives grouped under seven cross-cutting domains, each objective pointing at tools (documents hosted on the toolkit, or external links), deliverable key questions, challenges and technical terms.
